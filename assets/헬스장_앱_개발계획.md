# 헬스장 회원 관리 앱 — 개발 계획서

> 현직 트레이너(관리자 레벨) 인터뷰 답변을 반영한 기획·개발·테스트 로드맵
> 목표: 데모 → 친구 피드백 → 다듬기 → B2B 사업화
> 최종 수정 기준일: 2026-05-22

---

## 0. 인터뷰에서 도출한 핵심 설계 원칙 (북극성)

모든 의사결정은 아래 4가지 기준으로 판단한다. 친구 답변 20번에서 직접 인용한 트레이너의 실제 채택 기준이다.

1. **수업 끝나고/중간에 바로 쓸 만큼 간단한가** — 복잡하면 현장에서 안 쓴다. (답변 8, 11, 12, 20 반복)
2. **재등록과 매출에 도움이 되는가** — 트레이너가 돈 내고 쓸 유일한 이유. (답변 5, 14, 17, 20)
3. **회원과의 마찰을 줄여주는가** — 노쇼/취소/환불 분쟁. (답변 6, 7, 20)
4. **트레이너의 귀찮음을 덜어주는가** — 카톡 과부하 해소. (답변 12, 20)

### 포지셔닝
- "운동 기록 앱"이 아니라 **"회원 관리 앱"** 으로 인식되게 한다. (답변 20 명시)
- 기존 회원권 프로그램(터치짐, 브로제이 등)과 **겹치지 않는 영역**으로 차별화한다. 그들은 회원권/결제/출입을 잡고 있고, 우리는 그들이 비워둔 **PT 수업 내용·회원 관계·재등록 세일즈** 영역을 노린다. (답변 2, 19)

## 1. 제품 구조 — 3개의 사용자 앱(또는 모드)

인터뷰에서 "관리자용 앱은 따로 만들어야 할 듯"(답변 17)이라고 명확히 나왔다. 역할별로 화면과 권한이 크게 다르므로 **하나의 코드베이스 / 역할 기반 분리**로 간다.

| 역할 | 핵심 목적 | 대표 기능 |
|------|-----------|-----------|
| **트레이너** | 수업 기록 + 회원 관리 + 재등록 | 수업 기록 템플릿, 회원 카드, 재등록 알림, 회원 채팅 |
| **회원** | 내 운동 확인 + 소통 | 운동 기록 열람, 변화 추이, 숙제/식단 피드백, 예약, 체형 분석 결과 |
| **관리자(센터장)** | 매출·이탈·트레이너 성과 | 재등록률/전환률 대시보드, 만료자·이탈자 선별, 트레이너 온보딩 |

> **권한 분리 핵심(답변 9):** 트레이너 전용 메모(성향, 재등록 가능성 등 회원이 보면 기분 나쁠 내용)는 회원에게 절대 노출하지 않는다. 이건 데이터 모델 설계 초기부터 필드 단위 가시성으로 박아야 한다.

## 2. 기능 우선순위 (MoSCoW)

### Must — MVP 필수 (답변 20의 "무조건 3개" + 매출 직결)
- **M1. PT 잔여 횟수 + 재등록 타이밍 자동 관리**
  - 회원별 잔여 횟수, 만료일, 수업 빈도, 재등록 예상 시점 자동 계산
  - "세션 반 소진", "5회 남음", "곧 만료" 자동 알림 (답변 16, 20)
  - 수업 전날 회원에게 안내 메시지 자동 발송 (답변 20)
- **M2. 수업 기록 템플릿 (1분 입력)**
  - 운동 종목·세트·무게·반복·컨디션·통증·다음 수업 메모
  - 빠른 입력 UX (이전 기록 복사, 자주 쓰는 종목 즐겨찾기) (답변 8, 12)
- **M3. 예약·변경·취소 기록 + 규정 자동 안내**
  - 노쇼/지각/당일취소 기록이 앱에 남고, 차감 규정이 자동 표시 → 분쟁 시 근거 (답변 6, 7, 20)
- **M4. 회원 카드 (프로필)**
  - 이름·연락처·등록일·만료일·잔여 횟수·운동 목적·경험·부상 이력·체형 특징·생활 패턴·가능 시간대 (답변 3, 5)
  - 트레이너 전용 메모 영역(분리) (답변 9)

### Should — 차별화·정착 강화 (데모 2차)
- **S1. 변화 추이(비포&애프터)** — 중량 상승 그래프, 인바디 추이, 전후 사진 (답변 5, 14) → 연장 세일즈 직결
- **S2. 회원 채팅 (소통 공간 이동)** — 카톡을 대체하는 게 아니라 "옮긴다". 단, **알림 시간대 설정**으로 사생활 경계 보호 (답변 12)
- **S3. FAQ 자동 응답** — 운동 상식 FAQ + PT 규정 FAQ를 분리 운영 (답변 13)
- **S4. 회원 셀프 운동 기록 (간단 입력)** — "어디가 아팠고 어떻게 했더니 나아졌다" 식의 초간단 입력 (답변 11)

### Could — 사업 확장 (B2B 본격화 단계)
- **C1. 관리자 대시보드** — 재등록률, OT→PT 전환률, 평균 PT매출, 노쇼율, 만료자/이탈자 선별 (답변 17)
- **C2. 트레이너 온보딩 + 회원 인수인계** — 센터별 규정/멘트 입력, 인수인계 시 회원 히스토리 자동 정리 (답변 18)
- **C3. AI 체형 분석** — 정면/측면/후면 + 촬영 가이드(그리드/발 위치/수평/거리). 첫 등록 + 4·8·12주 비교 (답변 14, 15)
- **C4. AI 식단 분석** — 사진 → 대략 칼로리/단백질 피드백 (답변 16)

### Won't (지금은 안 함)
- 회원권 결제·출입 통제 → 기존 프로그램 영역, 충돌 회피 (답변 2, 19)
- AI 운동 자세 영상 분석 → 기술 난이도·정확도 리스크 큼. 친구도 "가능할진 모르겠으나"라고 함 (답변 16). R&D 트랙으로 분리.

> **AI 기능 주의(답변 14):** 체형 분석 결과는 **트레이너가 먼저 보고 코멘트를 달아 전달**하는 흐름을 기본값으로. AI가 회원에게 직접 "라운드숄더입니다"라고 단정하지 않게 한다. 트레이너 권위 보호 + 오진 리스크 회피.

## 3. 단계별 로드맵 (Phase)

### Phase 0 — 기획·검증 (2~3주)
- 인터뷰 답변 기반 기능 명세 확정 (이 문서)
- 화면 흐름(유저 플로우) + 와이어프레임 (트레이너 앱 우선)
- 친구와 와이어프레임 1차 리뷰 → 화면 단위 피드백
- 데이터 모델 설계 (회원/세션/예약/권한 가시성)
- **산출물:** 와이어프레임, ERD, MVP 기능 명세서

### Phase 1 — 데모(MVP) 개발 (4~6주)
- 대상 역할: **트레이너 앱** 우선 (혼자 먼저 써볼 수 있어야 함)
- 범위: M1~M4 (Must 전부)
- 데이터는 클라우드 백엔드 + 로컬 캐시
- **산출물:** 트레이너가 실제 회원 몇 명 넣고 1~2주 굴려볼 수 있는 데모

### Phase 2 — 친구 실사용 + 다듬기 (3~4주)
- 친구가 본인 PT 회원 대상으로 실사용
- 매주 피드백 수집 (특히 "입력이 귀찮은 지점" 집중)
- S1(변화 추이), S2(채팅), S3(FAQ) 추가
- **산출물:** 정착 가능성 검증된 v0.9

### Phase 3 — 관리자 + 회원 앱 확장 (4~6주)
- C1(관리자 대시보드), C2(온보딩/인수인계)
- 회원 앱 정식 분리 (열람/예약/소통)
- 친구네 센터 단위 파일럿 제안 → B2B 첫 레퍼런스
- **산출물:** 센터 1곳 파일럿 가능한 v1.0

### Phase 4 — AI 기능 (6~8주, 병렬 R&D 가능)
- C3(체형 분석) 먼저 — 사진 기반이라 영상보다 안정적
- C4(식단 분석) 다음
- 자세 영상 분석은 별도 R&D 트랙 (정확도 검증 후 결정)
- **산출물:** AI 차별화 기능 탑재 v1.5

## 4. 기술 스택 — Android / iOS 동시 대응

소규모 1인(또는 소수) 개발 + 양 플랫폼 동시 출시가 목표이므로 **크로스플랫폼**을 강력 추천.

### 권장: Flutter 또는 React Native
| 항목 | Flutter | React Native |
|------|---------|--------------|
| 언어 | Dart | JavaScript/TypeScript |
| 강점 | UI 일관성, 성능, 카메라/그리드 오버레이 구현 깔끔 | 웹 지식 재활용, 생태계 큼 |
| 추천 상황 | 체형 분석 카메라 가이드(그리드/수평) UI가 핵심이면 유리 | 이미 JS/웹에 익숙하면 유리 |

> **추천:** 체형 분석의 **카메라 그리드·수평·발 위치 가이드 UI**(답변 15)가 제품 차별화 포인트라 커스텀 그리기가 강한 **Flutter**를 1순위로 제안. 단, 본인이 익숙한 스택이 있으면 그게 우선 — 데모 속도가 가장 중요.

### 백엔드 (BaaS로 빠르게)
- **Firebase** 또는 **Supabase** — 인증, DB, 푸시 알림, 스토리지(사진) 한 번에
- 알림(재등록·전날 안내)은 푸시 + (선택) 카카오 알림톡 연동 검토
- 사진/인바디 등 민감 데이터는 **암호화 저장 + 접근 권한 분리** 필수

### AI 파트
- 체형 분석: 포즈 추정(MediaPipe/관련 모델)으로 키포인트 추출 → 각도·비대칭 계산
- 식단 분석: 외부 음식 인식 API 또는 멀티모달 LLM 활용
- **개인정보·민감정보(신체 사진) 처리 동의 및 보관 정책**을 사업화 전 반드시 수립

### 협업·배포 도구
- 코드: GitHub (브랜치 전략 단순하게 — main + feature)
- 데모 배포: Android는 Firebase App Distribution 또는 APK 직접 전달, iOS는 TestFlight

## 5. 테스트 전략

### 개발 중 (각 Phase)
- 핵심 로직(잔여 횟수 계산, 재등록 시점, 차감 규정) **단위 테스트** 필수 — 매출/분쟁 직결이라 버그 치명적
- 위젯/화면 테스트로 입력 플로우 회귀 방지

### 디바이스 테스트
- **Android:** 보급형 + 중급기 1대씩 (저사양에서 카메라/그리드 끊김 확인)
- **iOS:** 구형 1대 + 최신 1대
- 다양한 화면 비율(특히 체형 촬영 화면) 확인

### 베타(친구) 테스트 — 가장 중요
- 친구에게 전달 시 **앱뿐 아니라 "어디서 막혔는지" 기록 요청**
- 측정 지표:
  - 수업 1건 기록에 걸린 **실제 시간** (목표: 1분 이내)
  - 하루 중 앱을 **자발적으로 열었는지** (정착 신호)
  - 회원이 셀프 기록/채팅을 실제로 썼는지
- 베타 배포: Android = Firebase App Distribution / Google Play 내부 테스트, iOS = TestFlight

### 출시 전
- Google Play / App Store 심사 가이드라인 점검 (특히 건강·신체 데이터, 사진 권한 고지)
- 개인정보처리방침 페이지 준비 (양 스토어 필수)

## 6. 리스크 & 대응

| 리스크 | 영향 | 대응 |
|--------|------|------|
| 입력이 귀찮아 트레이너가 안 씀 | 치명적 (정착 실패) | 1분 입력 원칙, 이전 기록 복사, 베타에서 입력 시간 직접 측정 |
| 기존 회원권 프로그램과 기능 충돌 | 영업 거부감 | 결제·출입은 건드리지 않음, PT/관계/세일즈 영역만 |
| AI 오진으로 신뢰 하락 | 브랜드 타격 | 트레이너 검수 후 전달, 단정적 표현 금지 |
| 신체 사진 등 민감정보 유출 | 법적·신뢰 | 암호화·권한 분리·동의·보관정책 사전 수립 |
| iOS 심사 반려(건강 데이터) | 출시 지연 | 권한 고지·정책 페이지 사전 준비 |
| 1인 개발 리소스 한계 | 일정 지연 | MVP 범위 엄격 고정, Could 이후는 파일럿 반응 보고 결정 |
