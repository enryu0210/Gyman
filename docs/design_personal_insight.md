> 상태: **설계 초안 (미구현)** · 작성일 2026-07-25
> 출처: 트레이너 피드백(2026-07-24) — *"개인화된 신체, 습관에 대한 피드백이 들어간 내용이 들어갔으면 좋겠다."*
> 상위: `docs/develop_plan.md` Phase 4 (신규 4.8). 결정 변경 시 develop_plan 먼저 갱신.
> 연계: 체형분석 `docs/design_body_analysis.md`(신체 축의 마지막 조각), 변화추이 S1(0023), 출석/셀프기록(0028).

## 0. 목적과 범위

### 0.1 무엇을 푸는가
"개인화"라는 말은 보통 새 데이터를 더 모으자는 뜻으로 읽히지만, **이 앱은 이미 개인화에 필요한 데이터를 거의 다 갖고 있다.** 문제는 데이터가 **화면마다 흩어져 있어 아무도 연결해서 읽지 않는다**는 것이다.

- 회원은 출석 달력에서 "12일", 변화추이에서 "스쿼트 70kg", 셀프기록에서 "컨디션 6" 을 각각 본다. **"그래서 나는 어떤 상태인가"는 아무 화면도 답하지 않는다.**
- 트레이너는 그 연결을 머릿속으로 한다 — 회원이 늘면 불가능해진다.

→ **흩어진 수치를 한 사람 단위로 합쳐 "당신은 이런 패턴입니다"로 바꾸는 것**이 본 기능이다.

### 0.2 왜 이게 가장 싼 개인화인가
| | 본 기능 |
|---|---|
| 신규 데이터 수집 | **0** — §1 표의 원천이 전부 이미 존재 |
| 신규 테이블·마이그레이션 | **0** — 회원 노출은 `outgoing_notifications` 재사용(§4) |
| 신규 의존성 | **0** |
| LLM 호출 | **선택적**(문장 다듬기만, §3.3). 수치·판단은 규칙기반 |
| CV/카메라 | **불필요** — 체형분석·고스트와 독립적으로 먼저 나갈 수 있다 |

→ 피드백 2건 중 "개인화 피드백" 쪽은 **CV 트랙을 기다리지 않고 지금 착수 가능**하다. 체형분석은 여기에 *신체* 축 한 조각(비대칭)을 나중에 더해주는 관계다.

### 0.3 비범위
- **의학적 판단·진단**(체형 교정 처방, 부상 진단, 영양 처방): 절대 비범위. §5 안전 원칙.
- 식단 분석(4.4), 자세 영상 분석(4.5).
- 회원별 자동 프로그램 생성(운동 처방): 트레이너의 영역 — 침범하면 제품 신뢰가 깨진다.
- 타 회원과의 비교·랭킹: 동기부여보다 이탈 위험이 커 비범위.

## 1. 데이터 원천 — 전부 이미 있다

| 축 | 원천 | 도출 지표 |
|---|---|---|
| **출석 습관** | `sessions`(done) + `self_workout_logs`(0028) | 주당 평균 운동일, 연속 스트릭, 요일 편중, 최근 4주 vs 이전 4주 증감 |
| **성실도** | `sessions.status` (`no_show`/`canceled`/`late_cancel`) | 노쇼·당일취소 비율, 최근 추세 |

## 2. 지표 → 인사이트 규칙 (규칙기반, 순수 도메인)

`domain/personal_insight.dart` — **순수 함수 + 단위테스트 필수**(develop_plan §5.1). LLM·플랫폼 의존 0.

```dart
enum InsightTone { good, watch, info }   // 칭찬 / 주의 / 사실

class Insight {
  final String key;          // 'attendance_drop', 'plateau_squat' ...
  final InsightTone tone;
  final String factText;     // 수치 사실 — 이 문장은 항상 참이어야 함
  final double? value;
  final int sampleSize;      // 근거가 된 표본 수 (신뢰도 표시·게이트용)
}
```

규칙 예시(전부 **사실 + 조건**, 진단 아님):
| key | 조건 | 문구(템플릿) | tone |
|---|---|---|---|
| `attendance_up` | 최근4주 운동일 ≥ 이전4주 × 1.2 | "최근 4주 운동일이 이전보다 {n}일 늘었습니다" | good |
| `attendance_drop` | 최근4주 ≤ 이전4주 × 0.6 | "최근 4주 운동일이 {n}일 줄었습니다" | watch |
| `weekday_bias` | 특정 요일 비중 ≥ 50% | "{요일}에 집중돼 있습니다" | info |
| `self_ratio_low` | 셀프기록/전체 < 0.2, 표본 ≥ 8 | "PT 없는 날 기록이 {p}%입니다" | info |
| `plateau` | 종목 최고중량 8주간 변화 0, 표본 ≥ 6회 | "{종목} 최고중량이 8주째 {w}kg입니다" | watch |
| `pain_repeat` | 같은 부위 통증 3회 이상 | "{부위} 통증이 최근 {n}회 기록됐습니다" | watch |
| `condition_drop` | 최근 5회 평균 ≤ 이전 대비 -2 | "컨디션 점수가 평균 {a}→{b}으로 낮아졌습니다" | watch |
| `body_recomp` | 체중 유지(±1kg) + 체지방↓ + 골격근↑ | "체중은 유지되며 체지방 {x}%↓, 골격근 {y}kg↑" | good |
| `asymmetry` | 4.2 어깨/골반 기울기 > 임계 | "좌우 어깨 높이차 {d}도" | watch |

**표본 부족 시 규칙 자체를 건너뛴다**(`sampleSize` 미달 → 미생성). 데이터 3건으로 "정체입니다"라고 말하는 게 이 기능의 가장 큰 실패 모드다.

## 3. 3층 구조 — 누가 무엇을 보는가

가시성 분리가 이 제품의 핵심 요구사항이라(CLAUDE.md), 인사이트도 **층을 나눠야 검수 게이트가 필요한 곳/불필요한 곳이 갈린다.**

### 3.1 PI-1 · 회원 "내 리포트" — **검수 불필요**
- 내용: **판단 없는 사실 수치만**. "이번 달 12일 운동 / 연속 5일 / 스쿼트 최고 70kg / 체지방 -1.2%".
- 왜 검수 없이 되나: 회원 본인이 **이미 각 화면에서 볼 수 있는 값을 모아 보여줄 뿐**이라 새 정보 노출도, AI 판단도 없다. 조언·경고 문구는 여기 넣지 않는다.
- 계산 시점: **화면에서 실시간 계산**(저장 0). 마이그레이션 0.
- 위치: `/member/records/report` (변화추이 S1 옆 탭) — 기존 회원 데이터 provider 재사용.

### 3.2 PI-2 · 트레이너 "코칭 인사이트" — **검수 불필요(트레이너 전용)**
- 내용: 판단 포함. `watch` 톤 전부 — 정체·통증반복·출석급감·이탈위험.
- 왜 검수 없이 되나: **회원에게 노출되지 않는다.** `member_notes.visibility='trainer_only'` 와 같은 층.
- 위치: 회원 상세(`features/trainer/member_card/`)에 "코칭 인사이트" 카드. 기존 카드들(메모·인바디·영상·셀프기록)과 co-locate.
- 가치: 트레이너가 회원 15명을 머리로 추적하던 걸 앱이 대신함. **수업 준비 시간 단축**이 직접 효과.

### 3.3 PI-3 · 회원 노출 개인화 코멘트 — **검수 필수, 기존 게이트 재사용**
- 내용: 트레이너 코멘트가 붙은 개인화 메시지("최근 4주 출석이 줄었는데, 다음 수업에서 스케줄을 같이 조정해봐요").
- **신규 테이블 없음** — 기존 `outgoing_notifications`(draft→approved→sent) 를 그대로 쓴다:
  1. 트레이너가 코칭 인사이트 카드에서 "회원 안내 만들기" → 인사이트를 **컨텍스트로 주입**해 `generate-message-draft`(기존 Edge Function) 호출
  2. draft 적재 → **AI 검수 허브(`/trainer/ai-review`)** 로 흘러감 → 승인 → 발송
  3. 회원은 `/member/notices` 에서 받음(RLS `notif_member_read_sent_only`)
- 즉 **AI-B(1.9)의 입력 품질을 올리는 작업**이지 새 파이프라인이 아니다. 검수 게이트·PII 마스킹·일일 한도·동의 확인이 전부 자동 상속된다.

> 이 3층 구조 덕분에 **신규 마이그레이션과 신규 RLS 정책이 0**이 된다. PI-1은 사실만이라 게이트 불필요, PI-2는 트레이너 전용이라 게이트 불필요, PI-3만 게이트가 필요한데 그건 이미 있다.

## 4. LLM 사용 범위 (경계 고정)

- **수치·조건 판정은 100% 규칙기반**(`domain/personal_insight.dart`). LLM 에게 계산을 시키지 않는다 — 환각이 곧 잘못된 코칭이 된다.
- LLM 은 **PI-3에서 문장을 다듬는 데만** 쓴다. 입력은 이미 확정된 `Insight.factText` 목록 + 톤 지시. 기존 `generate-message-draft` 프롬프트에 인사이트 블록을 얹는 형태.
- PII 마스킹(실명→`{{NAME}}`)·동의(`ai_consent`)·일일 한도(`ai_call_logs` 0017)는 기존 서버 가드 그대로 적용.
- **LLM 없이도 전 기능이 동작해야 한다** — PI-1/PI-2는 LLM 무관, PI-3도 규칙 템플릿 문구로 폴백(develop_plan §7 "LLM 장애 시 수동 폴백" 원칙).

## 5. 안전 원칙 (진단 금지)

체형분석 §1.3과 같은 논리를 텍스트에도 적용한다.
- **사실 → 조건 → 제안** 순서로만 말한다. "무릎에 문제가 있습니다" ✗ → "무릎 통증이 최근 3회 기록됐습니다. 트레이너와 확인해보세요" ○
- 의학·영양 처방 문구 금지. 통증 관련은 **항상 트레이너 상담 유도**로 끝낸다(FAQ 2.4에서 정한 톤과 동일).
- 표본 부족 시 침묵(§2). "데이터가 쌓이면 보여드릴게요" 가 틀린 인사이트보다 낫다.
- 회원에게 가는 판단(`watch` 톤)은 **반드시 트레이너 코멘트를 경유**(PI-3).

## 7. 단계적 구현 계획

- **PI-0. 도메인 먼저** — `personal_insight.dart` 규칙 + 단위테스트. UI·DB 없이 계산만. *가장 안전하고 되돌리기 쉬움.*
- **PI-1. 회원 리포트** — 사실 수치 카드(검수 불필요, 마이그레이션 0). **회원이 체감하는 첫 성과.**
- **PI-2. 트레이너 코칭 인사이트 카드** — `watch` 신호(정체·통증반복·출석급감). **트레이너 체감 가치가 가장 큰 지점.**
- **PI-3. 인사이트 → AI 안내 메시지** — 기존 검수 허브로 연결.
- **PI-4(후속).** 체형분석(4.2) 결과가 나오면 `asymmetry` 규칙 합류 → *신체* 축 완성.

각 단계 끝: analyze/test/build 통과 + develop_plan 갱신.

## 8. 미해결 결정 (구현 전 확정 필요)

1. **집계 기간 기본값**: 최근 4주 vs 8주. 주 2회 회원 기준 표본이 4주면 8건 — 정체 판정엔 부족. → 지표별로 다르게(출석 4주 / 정체 8주) 제안.
2. **`session_records.pain` 파싱**: 자유 텍스트라 "부위" 추출이 필요. 키워드 매칭(무릎/어깨/허리…) vs 트레이너가 구조화 입력하도록 UI 변경. → 키워드 매칭으로 시작(마이그레이션 0), 정확도 부족하면 UI 개선.
3. **`condition` 필드 불일치**: `session_records.condition` 은 텍스트, `self_workout_logs.condition_score` 는 1~10. 두 축을 어떻게 합칠지(혹은 분리 표시).
4. **PI-1 실시간 계산 비용**: 회원 홈 진입마다 여러 테이블 조회 → 느려지면 요약 view 또는 캐시 필요(그때 마이그레이션 1건 발생).
5. **생성 주기**: 트레이너 수동 트리거 vs 월 1회 자동 적재(1.8 pg_cron 패턴 재사용). → **수동 시작**(AI-B/AI-C와 같은 결).
6. **`plateau` 의 정의**: "변화 0"은 너무 엄격 — ±2.5kg 이내를 정체로 볼지.

| 진단으로 읽힘(의료·법적) | 신뢰·법적 | 진단 문구 금지(§5) · 통증은 상담 유도 · 트레이너 검수 |

| `pain` 자유텍스트 파싱 정확도 | 오탐 | 키워드 매칭 보수적으로 + `watch` 는 트레이너 전용층(PI-2)에서 먼저 |
| 실시간 계산 성능 | 회원 홈 지연 | 표본 기간 제한 · 필요 시 view 승격(§8.4) |
| LLM 이 수치를 지어냄 | 잘못된 코칭 | **LLM 은 문장만**, 수치는 규칙기반(§4) · 검수 게이트 |
| 기능 과잉("잔소리 앱") | 이탈 | 한 번에 표시할 인사이트 **최대 3개** · `good` 톤 우선 노출 |

## 10. 요약

- **한 문장**: 새로 모으는 데이터 없이, 이미 흩어져 있는 출석·통증·중량·체성분을 한 사람 단위로 합쳐 **사실은 회원에게, 판단은 트레이너에게, 조언은 검수 후 회원에게** 3층으로 나눠 보낸다.
- **왜 지금인가**: 마이그레이션·의존성·신규 화면이 사실상 0이라 **CV 트랙(체형분석·고스트)을 기다릴 필요가 없다.** 피드백 2건 중 "개인화 피드백"의 대부분을 가장 먼저 회수할 수 있고, 체형분석 결과는 나중에 규칙 하나(`asymmetry`)로 합류한다.
