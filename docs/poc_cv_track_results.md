직접 겨냥한다 — §5 결정 대기 항목 참조.

## 1. `camera` 빌드 실패 — 원인과 회피책 ★

### 증상
```
Execution failed for task ':camera_android_camerax:compileReleaseJavaWithJavac'.
> class file for androidx.concurrent.futures.CallbackToFutureAdapter not found
```

### 원인
`camera_android_camerax` 의 자바 코드가 `CallbackToFutureAdapter` 를 직접 쓰는데,
그 클래스는 플러그인이 선언한 `implementation("androidx.camera:camera-core")` 의
**전이(transitive) 의존성**이다.
**AGP 9 는 전이 `implementation` 을 컴파일 클래스패스에 올리지 않는다** → javac 이 심볼을 못 찾는다.
(런타임엔 존재하므로 순수 빌드 타임 문제)

이 프로젝트 툴체인이 최신이라 터진 것: **AGP 9.0.1 / Gradle 9.1.0 / Kotlin 2.3.20 / Flutter 3.44**.

### 회피책 (적용됨)
`android/build.gradle.kts` 에 해당 서브프로젝트에만 의존성을 주입:
```kotlin
subprojects {
    if (name == "camera_android_camerax") {
        afterEvaluate {
            dependencies.add("implementation", "androidx.concurrent:concurrent-futures:1.2.0")
        }
    }
}
```
→ release/debug 빌드 모두 통과 확인.

### 남는 리스크
- **상류 플러그인이 고칠 때까지 유지해야 하는 임시 패치**다. `camera` 업그레이드 때마다 재확인 필요.
- 같은 원인(전이 implementation)이 **다른 플러그인에서도 터질 수 있다** — 앞으로 네이티브 플러그인을 추가할 때 같은 증상이면 같은 처방.

## 2. APK 크기 — ML Kit 이 비싸다

전부 **release** 빌드 실측.

| 구성 | fat APK(전 ABI) | arm64-v8a | armeabi-v7a |
|---|---|---|---|
| 기준선 (플러그인 추가 전) | 63.7MB | — | — |
| `+ camera` | 64.4MB | **25.2MB** | 23.0MB |
| `+ ML Kit pose` | 103.8MB | **47.3MB** | 41.7MB |
| **ML Kit 증가분** | +39.4MB | **+22.1MB** | +18.7MB |

> fat APK 는 전 ABI 를 합친 값이라 실제 배포 크기가 아니다. **arm64-v8a 47.3MB 가 요즘 기기의 실제 설치 크기**에 가깝다. Play 배포 시 App Bundle 을 쓰면 ABI 분리가 자동이다.

### 왜 이렇게 큰가 — 그리고 왜 못 줄이는가
`google_mlkit_pose_detection` 이 **두 모델을 다 번들한다**:
```gradle
implementation("com.google.mlkit:pose-detection:18.0.0-beta5")           // base(빠름)
implementation("com.google.mlkit:pose-detection-accurate:18.0.0-beta5")  // accurate(정확)
```
우리는 둘 중 하나만 쓰면 되지만, **플러그인 Kotlin 코드가 `AccuratePoseDetectorOptions` 를
import 로 직접 참조**해서 Gradle `exclude` 로 빼면 컴파일이 깨진다.

→ **줄이려면 플러그인을 포크해야 한다.** 유지보수 부담 대비 이득을 따져야 하는 선택.

### 선택지
| 안 | APK | 대가 |
|---|---|---|
| **A. 그대로 수용** | arm64 47.3MB | 설치 이탈률↑. 베타(친구·지인)엔 무해 |
| **B. 플러그인 포크** (모델 1개만) | 대략 35MB 추정 | 상류 업데이트 추적 부담 |
| **C. ML Kit 없이 간다** | 25.2MB | 체형분석 자동 수치·고스트 G2/G3 포기. **L1·L2 코칭은 이미 CV 없이 동작 중** |
| **D. 기능 분리 배포** | — | 앱 2개 운영 — 베타 규모엔 과함 |

**권고: 베타 동안 A.** 지금 사용자는 친구·지인이라 설치 크기가 이탈 요인이 아니고, 포크는
정식 배포가 가시화될 때 판단해도 늦지 않다. 단 **"체형분석을 켜는 순간 앱이 2배가 된다"는
사실을 결정 기록으로 남긴다** — 나중에 "왜 이렇게 큰가"를 다시 조사하지 않도록.

## 3. 만들어 둔 것

프로덕션 코드는 **한 줄도 건드리지 않았다.** 별도 진입점으로만 뜬다.

| 파일 | 역할 |
|---|---|
| `lib/main_poc.dart` | PoC 전용 진입점 + 메뉴 |
| `lib/poc/ghost_render_poc.dart` | PoC 1 — 카메라+영상 합성, 정렬 조작, **프레임 통계 패널** |
| `lib/poc/pose_analysis_poc.dart` | PoC 2 — 사진→ML Kit→수치, **`MlKitPoseAdapter` 포함** |
| `lib/poc/frame_extract_poc.dart` | PoC 3 — 영상→프레임→ML Kit, 두 탐색 모드 비교 |
| `android/.../VideoFrameExtractor.kt` | PoC 3 네이티브 — `MediaMetadataRetriever` 프레임 추출 |
| `android/.../MainActivity.kt` | PoC 3 채널 등록 (`gyman/poc_video_frames`) |

### `MlKitPoseAdapter` 는 버리는 코드가 아니다
B단계의 실제 산출물이다. ML Kit 은 랜드마크를 **이미지 픽셀 좌표**로 주고 도메인은
**정규화(0~1)** 를 받으므로, 그 변환을 어댑터가 책임진다. 덕분에
`posture_metrics.dart` 는 계속 ML Kit 을 모르는 순수 Dart 로 남아 테스트가 유효하다.

### PoC 1 — 고스트 실현성 ✅ **통과 (2026-07-27)**

측정 기기: **Galaxy Z Flip 3 (SM-F711N, Snapdragon 888 / 2021)**.
**의도적으로 구형 기기를 골랐다** — 여기서 60fps가 나오면 최신 기기는 볼 것도 없다.

| 구간 | raster 평균 | 최악 | jank |
|---|---|---|---|
| 카메라만 (1 텍스처) | 3.9ms | 22.0ms | 0.1% (1/687) |
| **카메라 + 고스트 (2 텍스처)** | **4.8ms** | 12.8ms | 0.0% (0/996) |
| + 드래그·좌우반전 | 3.2ms | 14.9ms | 0.0% (0/1106) |
| + 핀치줌 | 5.2ms | 14.9ms | 0.0% (0/5310) |
| **+ 발열 3분 31초** | **4.8ms** | 50.4ms | **0.1% (6/11116)** |

**판정: 통과.** 사전 고정한 기준 3개 전부 충족 — 평균 ≤ 16.7ms(예산의 29%), jank < 5%, Thermal Status ≤ 2.

**결론 두 가지.**
1. **영상 레이어 추가 비용은 +0.9ms.** 설계가 걱정한 "카메라+영상 동시 렌더 부하"는 **사실상 논점이 아니었다** — GPU 합성이라 텍스처 1장 추가가 거의 공짜다. 고스트 설계에서 성능은 제약 조건에서 빼도 된다.
2. **정렬 조작 3종(드래그·좌우반전·핀치줌)이 전부 성능에 무해하다.** 매 프레임 변환 행렬만 바꾸므로 재합성 비용이 없다. 즉 **고스트의 난점은 성능이 아니라 정렬 UX**라는 설계 문서의 판단이 실측으로 확인됐다.

**발열**: 3분 31초 무전원 구동(배터리 로그 `usb:false` 구간으로 확인). Thermal Status가 **1 LIGHT → 2 MODERATE** 로 한 단계 올랐는데도 **평균 raster는 4.8ms 그대로**였다. 888이 실제로 클럭을 낮췄는데 프레임 예산엔 영향이 없었다 — 여유가 그만큼 컸다.

| 센서 | 전 | 후 |
|---|---|---|
| AP (SoC) | 43.0°C | 44.3°C |
| SKIN | 39.7°C (status 1) | 40.7°C (status 2) |

**⚠ 이 수치의 한계 — 과신 금지.**
- **발열 구간이 격리되지 않았다.** 발열 테스트 직전에 `통계 리셋`을 누르지 않아 11116프레임 표본에 앞선 조작 구간이 섞여 있다. "발열 3분 30초만의 수치"가 아니며, 평균이 후반 저하를 희석했을 수 있다.
- **프레임 수가 적다.** 리셋(13:32)부터 15분간 11116프레임 = 평균 12fps. 60fps 연속 렌더링이었다면 5만 프레임이 나와야 한다 → 화면 꺼짐/백그라운드 구간이 있었다는 뜻이라 **"3분 연속 렌더링"이 온전히 검증되진 않았다.**
- 최악 50.4ms 스파이크는 6프레임뿐이라 지속적 저하가 아니다(충전 상태 변화 등 시스템 이벤트 추정).
- **원인**: adb 가 USB 케이블로 물려 있는데 발열 테스트를 위해 케이블을 뽑아 **3분간 원격 계측이 끊겼다**. 다음에 무전원 계측을 할 땐 **`adb tcpip` 로 Wi-Fi 전환 후** 뽑을 것.

→ **평균이 예산의 29%라 후반 저하가 있었더라도 33ms를 넘길 여지가 거의 없어, 베타 판단 근거로는 충분하다고 보고 통과 처리.** 정밀 수치가 필요해지면 Wi-Fi adb 로 3분 격리 재측정.

### PoC 2 — 체형분석 실현성
1. **정면 전신** 사진으로 촬영/선택 (전신이 다 나와야 함)
2. 어깨·골반 수치가 나오는지, 추론 시간이 몇 ms 인지 확인
3. **옆으로 돌아서** 한 장 더 → "정면으로 다시 촬영해 주세요" 가 뜨는지 (가드 동작 확인)
4. 같은 자세로 2~3장 → **수치가 얼마나 흔들리는지** (설계 §1.3 의 재현성 우려)

| 판정 | 기준 |
|---|---|
| ✅ 통과 | 정면 전신에서 두 수치가 나오고, 같은 자세 반복 시 **±1도 이내** |
| ⚠ 조건부 | 수치는 나오나 반복 편차가 큼 → 촬영 가이드(4.1) 강화 필요 |
| ❌ 실패 | 검출 자체가 안 됨 → 온디바이스 방향 재검토 |

> 4번(재현성)이 특히 중요하다. **수치가 촬영마다 3도씩 흔들리면 "4·8·12주 비교"가 의미를 잃는다.**
>
> ⚠ **재현성은 "같은 사진을 3번 분석"으로 재면 안 된다.** ML Kit 은 결정론적이라 수치가
> 완벽히 일치하고, 그건 아무것도 증명하지 못한다. 실제 회원은 4주 뒤에 **다시 서서 다시 찍는다** —
> 반드시 **같은 자세로 재촬영한 3장**이어야 한다. 폰을 고정하고 발 위치를 표시한 뒤,
> 매번 카메라 앞에서 완전히 벗어났다가 다시 서서 찍는다(안 움직이고 연속 촬영하면 편차가 인위적으로 작게 나온다).

#### 인터넷 사진을 쓴 선행 측정 — 절차와 기준 (2026-07-29, **측정 전 고정**)

직접 촬영 전에 **공개 사진으로 먼저 거를 수 있는 것**을 거른다. 하네스는
`lib/poc/pose_batch_poc.dart`(PoC 2-B 메뉴) — 여러 장 선택 → 순차 분석 → 편차 통계.

**⚠ 이 측정이 답할 수 없는 것부터 적는다.**
- **낙관 편향.** 스톡 사진은 스튜디오 조명·깔끔한 배경이라 헬스장에서 폰으로 찍는 실사용보다
  **쉬운 조건**이다. PoC 1 에서 구형 기기를 일부러 고른 것과 **정반대 방향의 편향**이라,
  여기서 통과해도 실사용 통과의 근거가 되지 않는다. 반대로 **여기서 실패하면 실사용은 볼 것도 없다.**
- **정답값(ground truth)이 없다.** 사진 속 인물의 실제 어깨 기울기를 모르므로 **절대 정확도는 못 잰다.**
  잴 수 있는 건 상대적인 흔들림뿐 — 단 회전 세트만은 예외다(아래).
- **진짜 재현성은 여전히 못 잰다.** 동일인이 같은 자세로 다른 시점에 촬영한 사진을 인터넷에서
  구할 수 없다. 아래 R 세트는 **하한 테스트**이지 재현성 측정이 아니다.

**사진 3세트 (Pexels 무료 라이선스, 저장소에 커밋하지 않음 — 타인 초상을 git 이력에 남기지 않기 위해).**

| 세트 | 구성 | 무엇을 재는가 |
|---|---|---|
| **set1** | 정면 전신 6장(이상적 직립 / 한 발 앞 / 한 손 주머니 / 손 허리 / 인물 작고 배경 복잡 / 팔짱) + **음성 표본 2장**(완전 측면, 상반신만) | 검출 여부 · 추론 시간 · **가드 동작** |
| **set2 (R)** | 기준 사진 1장 + 그 변형 3장 — 이동 ±14px · 확대축소 ±3% · 밝기 ±8% · JPEG 재압축. **회전 없음** | **재현성 하한** |
| **set3 (T)** | 같은 기준 사진을 −2° / −1° / +1° / +2° **회전**만 | **회전 응답 = 계산식 정확도** |

**set3 이 왜 정확도를 재는가.** `posture_metrics.dart` 의 각도는 `atan2` 의 절대값이라
이미지를 θ 만큼 회전시키면 측정값도 **정확히 θ 만큼** 움직여야 한다. 정답값이 없는 사진에서도
"얼마나 변해야 하는지"는 우리가 알고 있으므로, 이것만은 절대 검증이 된다.
CCW(+) 회전 → 이미지상 오른쪽이 위로 → **피사체 왼쪽 어깨가 그만큼 높아진다**
(하네스는 피사체 왼쪽이 높으면 +, 오른쪽이 높으면 − 로 부호를 붙인다).

**판정 기준 — 수치를 보기 전에 고정한다.**

| 세트 | ✅ 통과 | ❌ 실패 |
|---|---|---|
| **set1 (검출)** | 정면 전신 6장 **전부 검출**, 그중 **4장 이상**에서 어깨·골반 둘 다 수치가 나옴 (가림이 있는 주머니·팔짱은 실패 허용) | 정면 전신에서 미검출이 나옴 |
| **set1 (가드)** | 측면 사진이 `insufficient` + "정면으로 다시 촬영해 주세요" · 상반신 사진은 골반이 `insufficient` | 측면 사진에서 수치가 그냥 나옴 (= 가드가 안 먹음) |
| **set1 (속도)** | 1장당 **2초 이내** | — |
| **set2 (R)** | 폭(최대−최소) **≤ 0.5도** | **> 0.5도 → 재촬영 재현성은 볼 것도 없이 실패** |
| **set3 (T)** | 모든 회전각에서 `\|측정 변화 − 회전각\| ≤ 0.5도` | 회전에 값이 안 따라오거나 부호가 뒤집힘 = **계산식 결함** |

> **R 세트를 왜 0.5도로 잡았나** (본 기준 ±1도보다 엄격한 이유).
> R 은 **자세 변화가 0** 인 조건이다. 실제 재촬영은 여기에 자세 흔들림이 얹히므로,
> 실사용 목표가 ±1도라면 자세 변화 0 인 조건에서는 그보다 확실히 작아야 한다.
> 절반을 문턱으로 둔다 — 여기서 이미 0.5도를 넘으면 자세 흔들림을 더한 실제 재촬영이
> ±1도에 들어올 길이 없다.
>
> **통과해도 "재현성 통과" 라고 쓰지 않는다.** R 세트 통과의 의미는 딱 하나 —
> **"조기 탈락은 면했으니 직접 촬영 측정을 할 가치가 있다"** 이다.

#### 측정 결과 (2026-07-29) — ❌ **재현성 실패**

측정 기기: **Galaxy Z Flip 3 (SM-F711N)**. 앱 내부 저장소에서 직접 읽기
(= `image_picker` 재압축을 거치지 않은 경로). 원시 로그는 `[POC2]` 태그로 logcat 에.

| 항목 | 결과 | 판정 |
|---|---|---|
| set1 검출 | **8/8**, 정면 전신 6장 **전부** 어깨·골반 수치 산출 | ✅ 통과 (기준 4장) |
| set1 가드 (측면) | `insufficient` + "정면으로 다시 촬영해 주세요" | ✅ 통과 |
| set1 속도 | 첫 장 805ms(모델 초기화 포함), 이후 **99~180ms** | ✅ 통과 (기준 2초) |
| **set2 (R) 재현성** | **어깨 폭 1.97도 · 골반 폭 1.80도** | ❌ **실패 (기준 0.5도의 4배)** |
| set3 (T) 회전 응답 | 방향·단조성 정상, 오차는 어깨 2/4·골반 3/4 이 기준 초과 | ⚠ 계산식은 정상, 아래 참조 |

##### 1. 검출·속도·가드는 문제가 없다

정면 전신이면 조건이 나빠도(인물이 작고 배경이 잡다한 사진, 손이 주머니에 있는 사진,
팔짱 낀 사진) **전부 검출됐다.** 측면 사진에서는 설계한 가드가 정확히 동작해
수치 대신 재촬영 안내가 나왔다 — `minSeparationRatio` 가 의도대로 먹었다.

> ⚠ **상반신 사진(08) 기준은 내가 틀리게 세웠다.** "골반이 프레임 밖이라 `insufficient`
> 가 뜰 것" 으로 잡았는데, 실제 사진은 허벅지 중간까지 나와 **골반이 프레임 안에 있었다.**
> 수치가 나온 게 정상이며 앱의 실패가 아니다. 판정 항목에서 제외한다.

##### 2. 재현성은 실패했다 — 그것도 크게

**자세 변화가 0** 인 조건에서, 이동 ±14px(1.4%) · 확대축소 ±3% · 밝기 ±8% · 재압축만으로:

| 세트 | 어깨 | 골반 |
|---|---|---|
| R0 (기준) | −2.85 | −1.72 |
| R1 | −2.22 | **+0.07** |
| R2 | −3.65 | −0.36 |
| R3 | −4.19 | −0.79 |
| **폭** | **1.97도** | **1.80도** |

> **골반은 부호까지 뒤집혔다** (R0 −1.72 → R1 +0.07). 크기만 흔들린 게 아니라
> **"어느 쪽이 높은가" 라는 정성적 판단조차 뒤집힌다.** 트레이너 화면에
> "오른쪽 골반이 높음" 이라고 띄운 뒤 다음 촬영에서 "왼쪽이 높음" 이 나올 수 있다는 뜻이다.

##### 3. 범인은 촬영 가이드로 못 막는다 ★ (set4)

실패한 김에 요인을 하나씩 분리해 다시 쟀다 — **무엇을 통제하면 줄어드는지** 알아야
촬영 가이드(설계 4.1)로 해결 가능한 문제인지 판단할 수 있기 때문이다.

| 변형 (기준 대비) | Δ어깨 | Δ골반 |
|---|---|---|
| 이동 14px (1.4%) | −0.21 | +1.62 |
| 확대 3% | +0.19 | +1.89 |
| 밝기 +8% | −0.34 | +0.70 |
| **이동 3px (0.3%)** | **−2.02** | +0.54 |
| JPEG 품질 60 (픽셀 동일) | −0.34 | +0.73 |

**변형 크기와 오차 크기에 상관관계가 없다.** 14px 이동이 0.21도를 만드는데
**3px 이동이 2.02도를 만든다.** 체계적 오차라면 있을 수 없는 결과다 —
ML Kit 의 랜드마크 추정이 입력 픽셀의 미세 변화에 **불연속적으로 반응**한다는 뜻이다.

> **이것이 이 PoC 의 핵심 결론이다.** 오차가 "이동이 크면 커진다" 였다면 발 위치 표시·
> 삼각대·조명 통제로 줄일 수 있다. 그런데 **눈에 보이지도 않는 3px 어긋남이 2도를 만든다면
> 어떤 촬영 가이드로도 못 막는다.** 픽셀 단위 정렬은 사람이 할 수 있는 일이 아니다.

**ML Kit 자체는 결정론적이다** — 같은 파일을 set1·set2·set4 에서 3번 분석해 어깨 −2.85 /
골반 −1.72 가 **세 번 모두 완전히 일치**했다. 즉 위 편차는 100% 입력 픽셀 차이에서 온다.
설계 문서가 "같은 사진 3번 분석으로 재현성을 재면 안 된다" 고 경고한 근거가 실측으로 확인됐다.

##### 4. set3 — 계산식은 결백하다

회전 θ 를 주면 측정값도 θ 만큼 움직여야 한다. 결과:

| 회전 | 어깨 기대 | 실측 | 오차 |
|---|---|---|---|
| −2° | −4.85 | −5.66 | −0.81 |
| −1° | −3.85 | −4.44 | −0.59 |
| +1° | −1.85 | −1.46 | +0.39 |
| +2° | −0.85 | −1.31 | −0.46 |

**부호·단조성은 전부 정상**이고 오차 크기(0.4~0.8도)는 set2 의 노이즈(SD 0.87)와 같은 수준이다.
즉 `posture_metrics.dart` 의 계산에는 결함이 없다 — **오차는 전부 ML Kit 랜드마크 단계에서 들어온다.**
이 구분이 중요하다: 우리가 고칠 수 있는 코드의 문제가 아니다.

##### 5. 이 결과의 한계 — 과신 금지

- **사진 한 장(기준선)의 변형이 전부다.** 다른 체형·복장·배경에서 같은 크기의 불안정성이
  나온다는 보장이 없다. 특히 3px 이동이 2도를 만든 것은 **그 사진의 특정 조건**일 수 있다.
- **스톡 사진이라 실사용보다 쉬운 조건**이다(측정 전 §에 적은 낙관 편향). 그런데도 실패했다는
  점이 오히려 결론을 강하게 만든다.
- **직접 촬영 재현성은 여전히 안 쟀다.** 다만 자세 변화 0 인 조건에서 이미 기준의 4배가
  나왔으므로, 자세 흔들림이 얹히는 실제 재촬영이 ±1도에 들어올 가능성은 사실상 없다.
- **`image_picker` 경로(quality 80 재압축)로는 교차 확인하지 않았다.** 다만 set4 에서
  JPEG 품질 60 이 0.34도밖에 안 움직였으므로, 압축이 결론을 바꿀 요인은 아니다.

##### 6. 회피책 후보 — ⚠ **계산일 뿐, 아직 측정하지 않았다**

**여러 장 찍어 중앙값/평균을 쓰는 것**이 유일하게 유망하다. 오차가 카오스적(= 서로 독립)이라면
n 장 평균의 표준편차는 `SD/√n` 로 줄어든다.

| 촬영 장수 | 기대 SD (set4 의 0.79 기준) | 0.5도 기준 |
|---|---|---|
| 1장 (현재) | 0.79 | ❌ |
| 3장 평균 | 0.46 | 아슬아슬 |
| **5장 평균** | **0.35** | ✅ 여유 |

**미검증 리스크가 크다.** ⑴ 오차가 정말 독립인지 확인 안 됨 — 같은 자세·같은 조명이면
편향이 공통으로 실려 평균해도 안 줄어들 수 있다. ⑵ 회원에게 매번 5장을 요구하는 UX 비용.
⑶ 골반은 어깨보다 더 흔들려(모든 변형에서 +0.5~+1.9) 더 많은 장수가 필요할 수 있다.

→ **검증하려면 같은 사진의 변형을 20~30장 만들어 "5장씩 묶은 평균" 의 분산을 재면 된다.**
하네스는 이미 있으므로 세트 폴더만 추가하면 되는 작업이다.

### PoC 3 — 영상 프레임 추출 실현성 ⚠ **조건부 (2026-07-28)**

측정 기기: **Galaxy Z Flip 3 (SM-F711N)**. 표본 5fps · 최대 폭 640px · 상한 120프레임.
대상: **27.9초 주행 영상**(움직임이 끊기지 않는 영상을 골랐다 — 화면 녹화처럼 정지 구간이 많은
영상은 "서로 다른 프레임" 지표를 콘텐츠 탓에 낮게 만들어 모드의 문제로 오독된다).

| 지표 | 키프레임 (CLOSEST_SYNC) | 정확 시점 (CLOSEST) |
|---|---|---|
| 성공 / 실패 | 120 / 0 | 120 / 0 |
| **★ 서로 다른 프레임** | **25 (21%)** | **120 (100%)** |
| 프레임당 | **105.2ms** | **449.5ms** |
| 총 소요(120프레임) | 12.6초 | 53.9초 |

ML Kit(stream+base) 이어붙이기: 120프레임 **6.3초 · 프레임당 52.8ms** — 파이프라인은 끝까지 이어진다.
썸네일 육안 확인 결과 프레임 깨짐 없음.

#### 판정: ⚠ 조건부 — **정확도는 통과, 속도가 4.5배 초과**

**2분 영상 환산** (5fps = 601프레임, 위 실측치 선형 환산)

| 모드 | 추출 | + ML Kit | **합계** | 기준 60초 |
|---|---|---|---|---|
| 키프레임 | 63.2초 | 31.7초 | **94.9초** | ❌ (게다가 서로 다른 프레임 21%) |
| **정확 시점** | **270.1초** | 31.7초 | **301.8초 (5분)** | ❌ **4.5배 초과** |

**결론 세 가지.**

1. **"되는가"엔 답이 나왔다.** 플랫폼 채널 + `MediaMetadataRetriever` 경로가 성립하고, 정확 시점
   모드는 **서로 다른 프레임 100%** 로 표본추출이 온전히 된다. 신규 의존성 0 도 유지됐다.
   → **4.6·L3 를 재설계해야 하는 최악은 피했다.**
2. **막힌 건 속도다.** 정확 시점 모드가 키프레임 모드보다 **4.3배 느리다**(449.5 vs 105.2ms).
   설계 §7 결정 #2 가 "수동 트리거"를 검토한 이유가 실측으로 확인됐다 — 5분은 트레이너가
   기다릴 수 있는 시간이 아니다. **자동/동기 처리는 이 수치로는 불가능하다.**
3. **키프레임 간격이 약 1.12초다**(27.9초 ÷ 25 distinct). 5fps(0.2초 간격) 요청이 애초에
   이 영상에선 의미가 없었다는 뜻이고, **이게 회피책의 실마리**다(아래).

#### 회피책 후보 — ⚠ **계산일 뿐, 아직 측정하지 않았다**

프레임당 실측치를 프레임 수에만 곱한 값이다. 표본 fps 를 바꾸면 **키프레임 모드의 중복률이
같이 바뀌므로**(간격이 넓어질수록 중복이 줄어든다) 아래 표의 키프레임 행은 **정확도가 미검증**이다.

| 조합 (2분 영상) | 추출 + ML Kit | 60초 기준 | 미검증 리스크 |
|---|---|---|---|
| 정확 시점 · 1fps (121프레임) | **60.8초** | 아슬아슬 | 시점 정확도는 유지됨 |
| **키프레임 · 1fps** (121프레임) | **19.1초** | ✅ 여유 | **중복률 미측정** — 키프레임 간격 1.12초와 요청 간격 1초가 어긋나 일부 중복 가능 |
| 키프레임 · 2fps (241프레임) | 38.1초 | ✅ | 중복률 미측정 (간격 0.5초 < 1.12초라 **중복 확실**) |

**가장 유망한 건 "키프레임 모드 + 1fps"** — 어차피 키프레임이 1.12초 간격으로 존재하니
1초 간격 요청은 대부분 다른 키프레임에 걸린다. 그러면 **정확 시점 모드를 안 써도 되고 속도는 5배**다.
다만 `_sampleFps` 가 상수라 **코드를 고쳐 재측정해야 확인된다.**

#### ⚠ 이 수치의 한계 — 과신 금지

- **영상 한 편이 전부다.** 키프레임 간격은 촬영 앱·코덱 설정에 좌우되므로 **다른 영상에서 이 결론이
  그대로 성립한다는 보장이 없다.** 특히 대상은 27.9초 **주행 영상**이고, 실제 수업 영상은
  **2분·고정 카메라**라 조건이 다르다.
- **환산은 선형 가정이다.** 실측은 120프레임까지고, 601프레임을 연속 처리할 때 발열·메모리로
  프레임당 비용이 올라갈 수 있다.
- **최선 조건에서 잰 값이다.** USB 충전 중 + Thermal Status 1(AP 36.6°C)이라 스로틀링이 없었다.
  실사용(무전원·발열)에선 **더 느려질 수 있다.**
- **ML Kit 검출률은 측정하지 못했다** — 대상 영상에 사람이 없다. 판정 3개 기준 중 이 항목만 공란이다.

#### 뜻밖의 소득 — ML Kit 오검출이 실제로 관측됐다 ★

사람이 **한 명도 없는** 주행 영상인데 **120프레임 중 30프레임(25%)에서 인물이 검출됐다.**
설계 `design_class_video_tracking.md` §7 의 "다중 인물·복잡 배경 오검출 → 엉뚱한 프레이밍" 리스크가
가설이 아니라 **실측으로 확인된 것**이다.

→ **4.6 착수 시 반영할 것:** 검출 결과를 그대로 쓰면 안 된다. 랜드마크 **신뢰도(`likelihood`) 하한**과
**시계열 일관성**(직전 프레임 bbox 대비 급격한 이동은 버림)으로 걸러야 한다.
`shipped.md` §3.6 "틀린 정보를 띄우느니 아무것도 안 띄운다" 가 여기에도 적용된다 —
**오검출로 엉뚱한 데를 확대하느니 원본을 보여주는 게 낫다.**

### PoC 3 원본 설계 메모 (측정 전 작성)

`design_class_video_tracking.md` §7 "미해결 결정 #1" / §8 최상위 리스크에 답하는 PoC.
**여기서 막히면 4.6(자동 프레이밍)과 4.8 L3(자동 검출)이 통째로 재설계다.**

**수단: 플랫폼 채널 + `MediaMetadataRetriever` (신규 의존성 0).**
`video_thumbnail` 같은 플러그인 대신 Android 내장 API 를 직접 부른다 — 의존성 추가는
늦을수록 좋고(CLAUDE.md), `camera` 에서 이미 AGP 9 전이 의존성에 물린 터라
네이티브 플러그인을 하나 더 늘리는 쪽이 리스크가 컸다. 대가는 Kotlin 코드와 Android 전용
(iOS 는 나중에 `AVAssetImageGenerator` 로 대응).

**이 PoC 의 진짜 질문은 "되는가"가 아니라 "어느 모드가 쓸 만한가"다.**

| 모드 | 성격 |
|---|---|
| `OPTION_CLOSEST_SYNC` (키프레임) | 빠르지만 **시점이 부정확** — 키프레임 간격이 2초면 5fps 요청에 **같은 프레임이 10번 나온다** |
| `OPTION_CLOSEST` (정확 시점) | 정확하지만 **느리다** — 직전 키프레임부터 순차 디코딩 |

그래서 같은 영상에 두 모드를 다 돌려 **소요 시간**과 **실제로 서로 다른 프레임 수**를 함께 잰다.
중복 판별은 비트맵 픽셀 해시로 한다 — `MediaMetadataRetriever` 가 반환 프레임의 실제
타임스탬프를 알려주지 않아 이 방법뿐이다.

측정 절차 (표본 5fps · 최대 폭 640px · 상한 120프레임)
1. `PoC 3` 진입 → `영상 선택` (갤러리 영상 아무거나, **길수록 좋다**)
2. `추출 실행 (두 모드)` → 두 카드의 수치 비교
3. `ML Kit 이어서` → 뽑은 프레임이 실제로 ML Kit 에 들어가는지 + 검출률·속도
4. 하단 썸네일로 **프레임이 깨지지 않았는지 눈으로도 확인** (수치만으론 못 잡는다)

| 판정 | 기준 |
|---|---|
| ✅ 통과 | 정확 시점 모드에서 **서로 다른 프레임 90% 이상** + **ML Kit 검출률 80% 이상** + **2분 영상 환산 60초 이내** |
| ⚠ 조건부 | 서로 다른 프레임은 나오나 환산 시간이 김 → 표본 fps 를 낮추거나(2fps) 백그라운드 처리 + 진행률 UI 필요 |
| ❌ 실패 | 두 모드 다 중복 프레임만 나오거나 추출 자체가 실패 → **4.6·L3 재설계** |

> **검출률 80% 를 기준으로 잡은 근거** (2026-07-28, 측정 전 고정).
> 설계 §7 리스크표가 검출 실패를 **"이탈 프레임 홀드 + 보간"**으로 메우게 돼 있어 100% 는 필요 없다.
> 다만 5fps 표본에서 20% 를 놓치면 평균 1초에 한 프레임꼴이고, 그 이상 놓치면 보간이 사실상 추측이 된다.
> **연속 실패가 3프레임(0.6초)을 넘는 구간이 있는지도 함께 본다** — 총 검출률이 같아도 실패가 뭉쳐 있으면 크롭 경로가 튄다.
>
> ⚠ **검출률은 사람이 전신으로 찍힌 영상에서만 의미가 있다.** 풍경 영상의 검출률 0% 는 실패가 아니라 **측정 자체가 무의미**한 것이다.
> 그래서 이 PoC 는 두 갈래로 잰다 — **⑴ 추출 성능(서로 다른 프레임·환산 시간)은 아무 영상이나**, **⑵ 검출률은 인물 영상으로.**

> **전체 영상 환산 시간**이 이 PoC 의 결론이다. 트레이너가 "프레이밍 만들기"를 누르고
> 10초를 기다리는 것과 5분을 기다리는 것은 완전히 다른 기능이 된다
> (설계 §7 결정 #2 "수동 트리거" 판단의 근거 자료).

## 7. PoC 앱을 프로덕션과 나란히 설치하기 ★

```bash
flutter run   -t lib/main_poc.dart -Ppoc=true   # → com.gyman.poc  (PoC 하네스)
flutter build apk --debug                       # → com.gyman.gyman (프로덕션, 그대로)
```

`android/app/build.gradle.kts`:
```kotlin
applicationId = if (project.hasProperty("poc")) "com.gyman.poc" else "com.gyman.gyman"
```

**왜 product flavor 가 아닌가.** flavor 를 추가하면 Flutter 가 **모든** 빌드에 `--flavor` 를
요구해서 CLAUDE.md 의 검증 명령(`flutter build apk --debug`)이 깨진다. Gradle 프로퍼티는
안 넘기면 없는 것과 같아 기존 명령이 전부 그대로 산다. `-P` 는 `flutter run`·`flutter build`
양쪽 다 지원한다(`--android-project-arg` 의 축약).

**검증 완료 (2026-07-27)** — 병합 매니페스트로 확인:
- `-Ppoc=true` 빌드 → `package="com.gyman.poc"` ✅
- 기본 빌드 → `package="com.gyman.gyman"` ✅ (17.4초, 회귀 없음)

> **이 설정이 없던 시절의 사고**: 2026-07-26 에 `applicationId` 를 로컬에서 임시로 고쳐
> PoC 를 설치하고 되돌렸는데, 커밋이 안 돼 git 이력 어디에도 남지 않았다. 다음 날
> `flutter run -t lib/main_poc.dart` 를 그냥 돌렸으면 **프로덕션 앱을 덮어썼을 것.**
> 임시로 고친 빌드 설정은 반드시 저장소에 남기거나 즉시 되돌릴 것.
