# 수업 영상 객체 트래킹·자동 프레이밍 설계 (Class Video Auto-framing)

> 상태: **설계 초안 (미구현)** · 작성일 2026-07-21
> 출처/상위: `docs/develop_plan.md` Phase 4 (신규 4.6). 상위 영상 시스템은 `docs/design_class_videos.md`.
> 결정 변경 시 develop_plan 먼저 갱신.
> 핵심 결정(제안): **처리는 100% 온디바이스**(ML Kit) + **재인코딩 없이 "크롭 경로" 메타만 저장 → 재생 시점 팬/줌**. FFmpeg·서버 영상 파이프라인 미도입. LLM 미사용.
> 안전 원칙(재사용): 영상은 트레이너가 의도적으로 올리는 자료라 검수 게이트는 없음(영상 시스템과 동일). 단 **원본은 절대 훼손하지 않는다**(비파괴 처리).

---

## 0. 목적과 범위

### 0.1 무엇을 푸는가
트레이너가 올린 **수업 영상(폼 체크 짧은 클립)**이 손으로 들고 찍어 **흔들리거나, 회원이 프레임 밖으로 벗어나** 복기 가치가 떨어지는 문제를 푼다.
- **인물(피사체)을 인식해** 그 위치를 따라가는 **부드러운 크롭 창**을 만들면, 두 가지가 한 번에 해결된다:
  1. **손떨림 완화** — 크롭 창을 저역통과(low-pass) 필터로 부드럽게 이동시키면 프레임 간 미세 흔들림이 상쇄돼 안정화 효과.
  2. **자동 프레이밍** — 운동하는 회원이 항상 화면 중앙에 잡히게(오토 팔로우).
- 회원 가치: 흔들림 없이 내 자세를 또렷이 복기 → 재등록 동기·신뢰 ↑ (변화추이 S1·영상 보관과 같은 결).
- 트레이너 가치: "삼각대 없이 손으로 찍어도" 볼 만한 영상이 나옴 → 업로드 마찰 ↓.

### 0.2 왜 이 방식인가 (앞서 검토한 대안 대비)
손떨림/영상 처리 방향 검토(2026-07-21)에서 4개 경로를 비교했고, 아래 이유로 **온디바이스 트래킹 + 비파괴(재생시점) 프레이밍**을 택한다:
- **서버 영상 파이프라인**: Supabase Edge Function(Deno)엔 FFmpeg 없음 + 메모리·실행시간 제한 → 100MB+ 영상 처리 불가. 진짜 서버 처리는 **별도 FFmpeg 워커/외부 API = 새 인프라 + 월 비용 + 업로드 지연**. 단일 트레이너 베타엔 과함. Cloudflare Stream/Mux도 **안정화는 안 함**(트랜스코딩 전용).
- **온디바이스 재인코딩(FFmpeg vidstab)**: 핵심 플러그인 `ffmpeg_kit_flutter`가 사실상 유지보수 중단 + CPU·배터리 무겁고 느림.
- → **재인코딩 자체를 피한다**: 원본은 그대로 두고, 온디바이스로 **인물 위치만** 뽑아 크롭 경로(작은 JSON)로 저장. 재생할 때 플레이어가 그 경로대로 팬/줌. **재인코딩·서버·추가 저장 0.**

### 0.3 베타 범위 (스코프 가드)
- **온디바이스 검출만**: 인물 바운딩박스 추출·크롭 경로 계산은 전부 기기에서. 영상은 기존대로 비공개 버킷에 원본 저장, **처리 목적의 외부 전송 0.**
- 대상은 **단일 피사체**(운동 중인 회원 1명) 가정. 다중 인물·군중은 비범위.
- **비파괴**: 원본 영상 파일은 변경/재인코딩하지 않음. 효과는 앱 내 재생에만 적용(다운로드/외부 공유는 원본).
- 처리 트리거 = **트레이너 기기**(업로드 전/직후). 회원 기기 부담 0.

### 0.4 비범위 (후순위/별트랙)
- **자세 평가·렙 카운트·폼 교정 분석**(4.5 자세 영상 분석 R&D): 본 설계는 "프레이밍/안정화"만. 분석은 별트랙.
- **원본 재인코딩·내보내기(구운 영상)**: 다운로드/공유용으로 크롭을 실제로 구워내는 건 FFmpeg/네이티브 인코딩 필요 → C단계로 보류(§6).
- **실시간(촬영 중) 오토프레이밍**: 촬영 시점 처리는 카메라 파이프라인 복잡도↑ → 베타는 "촬영 후 처리".
- 다중 인물 추적, 얼굴 블러/익명화, 슬로모·하이라이트 자동편집.

## 1. 검출 엔진 결정 — 온디바이스 (제안)

### 1.1 왜 온디바이스인가
| 기준 | 온디바이스(채택) | 서버/클라우드(미채택) |
|---|---|---|
| 영상 외부전송 | **없음**(원본은 저장용만, 처리 목적 전송 0) | 있음 — 프라이버시 우선 설계와 충돌 |
| 인프라 | **추가 0**(앱 내 처리) | FFmpeg 워커/외부 API 신설 필요 |
| 비용 | **0**(호출당 과금 없음) | 처리 시간·전송 과금 |
| 업로드 지연 | 낮음(백그라운드 검출) | 서버 왕복·큐 대기 |

→ 체형분석(4.2)에서 확정한 "**민감 미디어는 온디바이스**" 원칙과 일치. ML Kit 의존성을 그 트랙과 공유.

### 1.2 라이브러리 후보
- **`google_mlkit_pose_detection`** (1순위) — 체형분석(4.2)에서 이미 도입 예정. 사람 33개 랜드마크 → **인물 바운딩박스** 도출이 안정적(단일 피사체에 강함). 재사용으로 의존성 증가 최소화.
- **`google_mlkit_object_detection`** (보조) — 객체 추적 ID 제공(프레임 간 동일 객체 추종). 회원이 프레임서 크게 벗어나 pose가 끊길 때 폴백. 단 헬스장 기구 등 일반 객체도 잡아 노이즈 가능.
- 프레임 추출: 영상에서 표본 프레임을 뽑아 검출에 넣어야 함 — `video_player`는 프레임 접근을 노출하지 않음 → **프레임 추출 수단 검증 필요**(§8 리스크). `video_thumbnail`류로 다중 시점 추출 or 네이티브 채널.
- ⚠ ML Kit·프레임추출 모두 **네이티브 플러그인 증가** → develop_plan §0 의존성 표 갱신 + 빌드 영향 점검 필수(체형분석과 동일 주의).

### 1.3 정확도·품질 한계 (정직하게)
- 표본 프레임 간격이 크면(예: 5fps) 빠른 움직임에서 크롭이 뒤늦게 따라감 → 저역통과 스무딩 + 보간으로 완화하되, 급격한 이동엔 한계.
- 크롭 = **디지털 줌**이라 잘라낸 만큼 해상도 손실. 원본 1080p에서 과도한 확대는 화질↓ → **최대 줌 상한**(예: 1.4x) + 여백(safe margin) 유지.
- pose가 잡히지 않는 프레임(피사체 프레임 이탈·가림)은 **직전 크롭 유지**(홀드) → 튐 방지.
- **결론:** "완벽한 짐벌"이 아니라 "손떨림·이탈을 눈에 띄게 줄이는 보조 효과". 원본이 항상 보존되므로 실패해도 손실 없음(비파괴가 안전장치).

## 2. 데이터 모델

### 2.1 `class_videos` 확장 (신규 마이그레이션)
실영상은 그대로. **크롭 경로·검출 메타만** 컬럼 추가(체형분석 `ai_result` provenance 패턴 재사용).

```sql
ALTER TABLE class_videos
  ADD COLUMN IF NOT EXISTS tracking_data jsonb,          -- 아래 §2.2 구조. NULL이면 미처리(원본 그대로 재생)
  ADD COLUMN IF NOT EXISTS tracking_status text          -- 'none'|'processing'|'ready'|'failed'
    NOT NULL DEFAULT 'none';
```
- 별도 테이블 대신 **컬럼**: 영상과 1:1이고 크롭 경로는 작음(수백 keyframe × 4 float ≈ 수 KB). RLS는 기존 `class_videos` 정책이 그대로 커버 → **추가 RLS 불필요**(§3).
- `tracking_status`로 UI가 "처리 중/완료/실패"를 구분. 실패해도 원본 재생은 정상.

### 2.2 `tracking_data` JSON 구조 (제안)
```jsonc
{
  "engine": "mlkit_pose",           // 엔진 식별
  "engine_version": "x.y.z",        // 패키지 버전 — 사후 재현/디버깅
  "processed_at": "2026-..Z",
  "source": { "w": 1080, "h": 1920, "duration_ms": 92000, "sample_fps": 6 },
  "zoom_max": 1.4,                   // 적용된 최대 디지털 줌 상한
  "keyframes": [                     // 표본 시점별 크롭 창(정규화 0~1, 원본 기준)
    { "t_ms": 0,    "cx": 0.50, "cy": 0.55, "scale": 1.20 },
    { "t_ms": 166,  "cx": 0.51, "cy": 0.55, "scale": 1.20 }
    // cx,cy = 크롭 창 중심 / scale = 확대율. 재생 시 t_ms 사이 선형보간.
  ]
}
```
- `keyframes`는 **저역통과 필터로 스무딩된** 크롭 창 경로(원시 bbox가 아님). 흔들림 완화가 여기서 일어남.
- 재생기는 현재 재생 위치에서 앞뒤 keyframe을 보간해 `Transform`(scale+translate) 적용.

## 3. 처리 아키텍처 (핵심)

### 3.1 파이프라인 (트레이너 기기, 업로드 직후 백그라운드)
```
원본 영상(업로드 완료)
   │
   ├─ 1. 프레임 표본 추출 (예: 6fps)                [온디바이스]
   ├─ 2. 각 프레임 ML Kit 인물 bbox 검출            [온디바이스]
   ├─ 3. bbox → 크롭 창(중심 cx,cy + 여백 scale)
   ├─ 4. 시계열 저역통과 스무딩(손떨림 상쇄) + 이탈 프레임 홀드
   ├─ 5. keyframe으로 다운샘플 → tracking_data JSON
   └─ 6. UPDATE class_videos SET tracking_data=…, tracking_status='ready'
```
- 원본은 이미 §영상시스템 플로우로 업로드됨(0027). 본 처리는 **그 위에 메타만 얹음** — 실패해도 영상 자체엔 영향 0.
- 처리는 무거우니 **업로드 성공 후 비동기**로. 진행 중 `tracking_status='processing'` 표시, 완료 시 provider invalidate.

### 3.2 재생 시점 적용 (비파괴 프레이밍)
- 회원/트레이너 재생기(`features/videos/class_video_player.dart`)에서 `tracking_data`가 있으면 **"자동 프레이밍 ON/OFF" 토글** 제공(기본 ON, 언제든 원본 보기 가능).
- ON일 때: `video_player` 텍스처를 `ClipRect` + `Transform`(현재 position에 보간된 `scale`/중심 이동)으로 감싸 팬·줌. `controller.position` 틱에 맞춰 크롭 창 갱신.
- OFF일 때: 기존 그대로 원본 렌더. **원본은 항상 1클릭 거리** — 처리 신뢰도 한계(§1.3)의 안전장치.

> 이 구조의 핵심 이점: **재인코딩·서버·추가 저장이 전혀 없다.** 원본 1개 + 수 KB JSON만으로 앱 내 안정화/프레이밍을 얻고, 다운로드/공유는 원본 그대로라 데이터 정합성 문제도 없음.

## 4. 동의·프라이버시

- 본 처리는 **외부 전송이 없으므로** `member_profiles.ai_consent`(외부 LLM 전송 동의)는 **불필요**. (체형분석과 같은 논리 — 온디바이스는 LLM 동의 대상 아님)
- 영상 자체의 **촬영·보관 동의**는 기존 영상 시스템 게이트(`design_class_videos.md` §3.4, 업로드 다이얼로그 "회원 동의" 체크)가 이미 커버 → **추가 동의 항목 없음**.
- audit: `tracking_data.engine_version`으로 어떤 엔진이 만들었는지 추적(develop_plan "AI 생성 콘텐츠 audit" 취지 충족).

## 6. 단계적 구현 계획 (제안)

- **PoC(선행, 필수)** — 가장 큰 미지수부터: **"영상에서 표본 프레임을 뽑아 ML Kit에 넣는" 경로가 성립하는지** 작은 실험으로 검증(§1.2·§8). 여기서 막히면 전체 재설계.
- **A. 도메인 + 스키마**: `domain/video_tracking.dart`(bbox→스무딩 크롭경로) + 단위테스트 → 마이그레이션(`tracking_data`/`tracking_status` 컬럼). *UI·ML 없이 계산부터.*
- **B. 온디바이스 처리**: 프레임추출 + ML Kit 인물검출 → 크롭경로 생성 → 업로드 후 비동기로 `tracking_data` UPDATE + 상태 표시.
- **C. 재생 시점 프레이밍**: 재생기 팬/줌 토글(기본 ON, 원본 1클릭). **여기까지가 사용자가 체감하는 MVP.**
- **D(별트랙, 보류)**: 원본 재인코딩·내보내기(구운 영상, FFmpeg/네이티브) — 다운로드/공유용. 무게·플러그인 리스크로 후순위.
- **E(별트랙)**: 자세 평가·렙 카운트(4.5)와 검출 파이프라인 공유 검토.

각 단계 끝: analyze/test/build 통과 + develop_plan 갱신(프로젝트 규칙).

## 7. 미해결 결정 (구현 전 확정 필요)
1. **프레임 추출 수단**: 순수 플러그인으로 표본 프레임 접근이 되는가, 아니면 네이티브 채널이 필요한가. → **PoC로 먼저 결론**(전체 실현성의 관문).
2. **처리 시점**: 업로드 직후 자동 vs 트레이너가 "프레이밍 만들기" 수동 트리거. → 배터리·비용 감각상 **수동 트리거**로 시작 검토(체형분석·메모 초안이 수동 트리거인 것과 같은 결).
3. **줌 상한/여백**: 화질 손실 vs 프레이밍 강도 트레이드오프(`zoom_max` 기본값).
4. **엔진 선택**: pose 단독 vs pose+object 폴백(피사체 이탈 대응).
5. **기본 토글 상태**: 재생 시 자동프레이밍 기본 ON vs OFF. (원본은 항상 접근 가능 전제)
6. **처리 실패 UX**: `tracking_status='failed'` 시 조용히 원본만 보일지, 재시도 버튼을 줄지.
